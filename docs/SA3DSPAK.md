# `.sa3dspak` version 1

All integers are unsigned little-endian. Files begin with a 48-byte header (`SA3DSPAK`, major/minor version, header/file sizes, TOC offset/count, flags, payload CRC-32, header CRC-32). Each 40-byte TOC entry contains a 16-byte NUL-padded type, 64-bit file offset and size, CRC-32, and flags. Chunks are 16-byte aligned.

Defined v1 concepts are `GEOMETRY`, `COLLISION`, `MATERIALS`, `TEXTURES`, `SET`, `CAMERA`, `AUDIO`, `METADATA`, and `ROUTE`. Their payload schemas are intentionally not invented here. Metadata records the source profile. Packages never contain host pointers, VAs, or RVAs.

The host and runtime validators check version, file size, count limits, all offset/size arithmetic, header/payload/chunk integrity, and reject malformed input before exposing a chunk. The runtime reader is allocation-free and returns views into a caller-owned buffer, allowing later streaming and Old 3DS budgeting.


## Sonic Emerald Coast route metadata

An optional external `emerald_coast_route.sa3dspak` enables the full terrain
profile; an absent or invalid route retains the bounded opening regression
profile. Generate it with `tools/build_pc2004_emerald_coast_route.py OWNER_EXE
EXTERNAL_OUTPUT`. It verifies the exact owner executable before reading original
starts and the normal act handoff. Generated bytes stay outside the code tree.

The `ROUTE` payload is little-endian: a32-byte header `<8sHHIIIII>` with magic
`SA3DECRO`, version1, flags0, level1, start count, edge count, start offset32,
and edge offset immediately after the starts. Each24-byte start `<IIfffI>`
contains act, character0(Sonic), task-origin XYZ and unsigned16-bit taskY in a
32-bit field. Each24-byte edge `<IIffff>` contains from/to act, task-origin
sphere center XYZ and strictly positive radius. Runtime counts are capped at8;
nonfinite data, duplicate starts/from-edges, self-edges, unknown references,
overlap/trailing bytes and unsupported versions are rejected. Native WCA accepts
exactly two starts(0,1) and one edge(0->1). This records source data, not a retail
trace or a claim that the full stage is playable.

Visual packages accept the four required chunks and optional single `SET` and
`CAMERA` banks. These optional banks are CRC-checked and retained, but their
presence alone does not activate gameplay objects or original cameras.


## Direct ring resources (partial gameplay object support)

`tools/build_pc2004_ring_assets.py OWNER_EXE SYSTEM EXTERNAL_OUTPUT` emits
`ring_visual.sa3dspak` (one identity Basic model and its one compactly remapped
source texture) and `ring_placements.sa3dspak` (`METADATA` + `RINGS`). Original
mesh vertices, UVs, material values and32-byte placement records remain external.
The current scope is direct class0 placements in the normal Sonic S variants;
line/group expansion is not implied. Missing/invalid optional resources retain
the existing terrain/controller profile and report the incomplete object state.

`RINGS` uses32-byte `<8sHHIIIII>` header: magic`SA3DRING`, version1, flags0,
actCount2, rowCount(1..2046), rowOffset32, specOffset(32+rowCount*40), totalSize.
Each40-byte row `<II32s>` contains act0/1, original SET row index(<1023), and
unaltered32-byte source row. Rows are strictly ordered by act then source index;
duplicate references, non-class0 entries and nonfinite floats are rejected.
The trailing32-byte spec `<ffffffII>` contains collision centerXYZ/radius,
load/unload squared ranges, unsigned16-compatible rotation step and cliplevel0..2.
The importer verifies the executable, source registry, normal Sonic suffix and
collision/display instructions. Cliplevel comes from owner`sonicDX.ini`, with
executable fallback1; high placement bits retain source clipping semantics.
No PC pointers or addresses occur in runtime payloads.


### Optional ring-group definitions

`build_pc2004_ring_groups.py OWNER_EXE SYSTEM DIRECT_PLACEMENTS EXTERNAL_OUTPUT`
adds `RING_GROUPS` to an existing placement package. It preserves the direct
`RINGS` payload and reuses the existing compact visual package. Source class21,
line/circle code, group journal, normal Sonic variant, bounds and the owner-only
Ninja quarter-wave lookup table are verified before conversion. Output remains
outside Git; the lookup table is Sega-derived data, not compiled into source.

`RING_GROUPS` header32bytes `<8sHHIIIII>`: magic`SA3DRGRP`, version1, flags0,
groupCount, rowOffset32, specOffset, trigOffset, totalSize. Each40-byte row has
act, source SET row index and preserved32-byte SET record. The32-byte spec
`<fffIIIII>` stores parent load/unload squared ranges, child unload squared range,
maximum child index7, lookup count1025 and three reserved zeros. The final4100bytes
are the owner's1025float32 quarter-wave samples. Source writer validates the
exact table digest; native reader validates finite, monotonic0..1 samples and
endpoints. Counts, types, row identity/order, cross-kind duplicates, modes,
parameters and all region arithmetic are bounded before actor allocation.

The runtime derives line/circle children using the original fractional count,
truncated BAMS angles and lookup interpolation. It applies Z–X–Y matrix order,
then adds parent translation once. Child rotations/parameters are zero. Original
parent activation, reverse child update order, byte collection journal and
child-unload parent teardown are separate from direct-ring residency. Combined
actor capacity remains2046 across both acts. Original source collision list7
capacity128 is retained for this ring subsystem; cross-category queue ordering
remains a later object integration requirement.
